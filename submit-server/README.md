# Приём сданных работ

Сайт курса статический (GitHub Pages) и принимать файлы не может. Студенты
сдают работы на странице `submit/` сайта, а файлы уходят сюда — на
маленький сервис на сервере преподавателя: `https://submit.konkin-nikita.ru`.

## Как это устроено

1. Студент вводит код группы. Страница открывает журнал (как это делает
   страница журнала) и берёт из него список ФИО и **открытый** ключ
   преподавателя.
2. Студент выбирает себя, работу и файл (`.ipynb`, `.pdf`, `.docx`, `.zip`,
   до 10 МБ) или пишет ответ текстом — например, ссылку. Ноутбук проверяется
   ещё в браузере: запущены ли ячейки, нет ли ошибок в выводе, та ли это
   работа (по заголовку `# …`). Текст уходит тем же конвертом как
   `ответ.txt`; его начало лежит и в заголовке, поэтому журнал показывает
   ответ прямо в списке.
3. Браузер шифрует ФИО, имя файла и сам файл этим ключом
   (ECDH P-256 + HKDF + AES-256-GCM, `site/crypto.js`) и отправляет конверт
   сюда. Студент получает квитанцию: номер и контрольную сумму.
4. Преподаватель входит в журнал по паролю. **Закрытый** ключ лежит только в
   ящике преподавателя, поэтому только там работы и расшифровываются: панель
   «Сданные работы», метки «сдано» в таблице, скачивание по одной или архивом.

Сервис не видит ни ФИО, ни содержимого: на диске только конверты
`data/<работа>/<время>-<случайное>.mlgs`. Поэтому список и конверты он отдаёт
без пароля. Защита от мусора — проверка разметки конверта, предел размера,
частоты отправок с одного адреса и общего объёма папки. Удаления через API
нет: лишнее удаляется на сервере из `data/`.

Ключ появляется сам при первом входе преподавателя в журнал (если в
`site/course.toml` задан `submit_url`). После этого журнал нужно один раз
**сохранить** — иначе страница сдачи ключа не увидит.

Ограничение: страница сдачи знает только код группы, поэтому сдать работу
«за другого» технически может любой, у кого есть код. Преподаватель видит
время и все версии; спорные случаи решаются квитанцией.

## Файлы

| файл | что это |
|---|---|
| `server.py` | сам сервис, только стандартная библиотека Python |
| `Dockerfile` | образ `python:3.12-slim`, запуск не от root |
| `compose-service.yaml` | сервис для `docker-compose.yaml` проекта с nginx |
| `nginx-submit.conf` | блок `server` для `nginx.conf` |
| `deploy.sh` | первое развёртывание: сертификат, контейнер, nginx |

Тесты — `tests/test_submit_server.py` в корне репозитория.

## Развёртывание

На сервере рядом с проектом nginx (`~/projects/ssl-nginx-docker`):

1. Скопировать эту папку в `~/projects/mlg-submit`.
2. Вставить `compose-service.yaml` в раздел `services` файла
   `ssl-nginx-docker/docker-compose.yaml` (сначала — резервная копия).
3. `sudo bash ~/projects/mlg-submit/deploy.sh` — получит сертификат
   Let's Encrypt, соберёт и запустит контейнер, добавит блок в `nginx.conf`
   (с копией и проверкой `nginx -t`) и проверит `https://…/health`.

Обновить код сервиса: скопировать новый `server.py` и выполнить
`docker compose up -d --build mlg-submit` в `ssl-nginx-docker`.

Локально:

```bash
HOST=127.0.0.1 DATA_DIR=./data ALLOWED_ORIGINS=http://localhost:8000 python server.py
```

## API

| запрос | ответ |
|---|---|
| `GET /health` | `ok` |
| `POST /api/submissions?work=<slug>` | тело — конверт; `201` и квитанция `{id, work, received, size}` |
| `GET /api/submissions` | все сдачи по времени: `{id, work, received, size, head}`; `head` — начало конверта до конца заголовка (base64) |
| `GET /api/submissions/<id>` | конверт целиком |

Отправка разрешена только со страниц из `ALLOWED_ORIGINS` (CORS и проверка
`Origin`). Остальные настройки — в начале `server.py`.
